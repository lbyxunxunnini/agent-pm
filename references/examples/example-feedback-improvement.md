# 反馈驱动改进示例

> 以下为模拟案例，用于展示判断过程，不代表真实项目、实跑或人工确认。

## 场景和问题

某 Skill 使用脚本整理用户提供的 Markdown 报告。用户反馈：报告中的两个同名章节有时只保留一个。假设检查脚本后发现其以标题为键写入字典，后出现的章节覆盖了前者；该证据可确认覆盖逻辑存在，实际使用频率和其他原因仍未知。

## 改进选择

- 根因位于确定性的数据转换：修改脚本以按原始顺序保留章节，比仅在 Skill 中提醒模型注意重复标题更直接。
- 增加包含两个同名标题的回归输入，检查两个章节及其顺序；同时复用普通报告样例，检查常规输入没有退化。无需为此增加统一 CLI。
- 将该失败输入作为项目回归案例属于建议；是否写入被审项目受用户授权和项目规则约束。一次反馈不自动变成 agent-pm 的跨项目正式规则。

## 验收与证据（示例格式，均未执行）

| 对象 | 方法 | 状态及证据 |
|------|------|-----------|
| 重复标题的两个章节及顺序 | 自动运行脚本，对照预期输出 | 未执行；尚无输出证据 |
| 普通报告 | 运行既有样例，对照原有预期 | 未执行；尚无回归证据 |
| 输出是否符合用户实际使用习惯 | 需要时由用户审阅 | 尚未确认；不预设为每次必需的门禁 |

若得到实际运行或用户确认结果，应分别记录输入、版本或环境、观察与限制；没有改前基线时说明无法进行改前后对照，不能由静态检查推断实跑通过。
