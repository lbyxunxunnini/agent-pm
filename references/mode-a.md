# 模式 A：审阅

目标：理解用户实际任务，识别影响目标达成的关键失败及根因，提供可验证的改进。清单用于补漏，不以覆盖维度、发现数量或缺少某种设计模式作为质量目标。

## 1. 理解目标与范围

确定目标项目、用户请求和本轮范围；从入口、说明、适用规则、真实使用记录或测试中理解：目标用户、典型任务、预期结果、主要约束和失败代价。事实不足时标明假设，不虚构用户经历。读取可访问且属于当前项目的历史问题记录，复用有效 issue_id 与状态；没有记录时在对话中维护。固定 ReviewSpec（范围、重点、排除项）；可按发现更新阅读线索，不把新线索视为扩大审查目标。

从入口沿核心执行路径追踪实际引用、状态转换和高影响分支，记录文件路径与职责。优先覆盖最可能影响目标的路径；不能覆盖时说明缺口。可以委托独立执行者读取，但摘要是索引而非证据替代品；允许按需查阅原文，未读或初判 pass 均不代表已验证。上下文有限时分批读取并保存索引，不设固定文件数上限。

## 2. 从任务和结果发现问题

选择与项目目标匹配的真实场景；没有可用实录时，构造具体输入和条件并标为推演。沿输入、关键决策、工具与交接、异常、终止到用户结果追踪。关注：能否解决用户任务、关键判断是否可执行、用户控制与授权是否正确、是否能观察并验证结果、复杂度是否有实际收益。

比较目标与行为，寻找最影响结果的失败及多个表面问题的共同根因；评估现有机制是否已经覆盖，避免把设计偏好当缺陷。再按 [checklist.md](checklist.md) 选择适用项补漏，清单是启发而非强制功能列表。必要时追溯实际运行记录、测试或实现以核实工作流，但不做通用代码质量审查。

## 3. 验证与判断

对每个准备作为已确认问题的候选：
1. 回读相关上下文和例外、跨文件引用，记录证据位置。
2. 以具体输入走完整路径；按需核实工具、实现或回退，区分推演与运行观察。
3. 区分功能缺陷、体验摩擦、文档精度与设计取舍，说明用户影响。
4. 结合项目目标判断概念和实现是否合理；考虑反证和已有保护。
5. 涉及时序或状态时追完相关逻辑链，解释触发条件、结果与因果关系。

证据分为静态材料、场景推演、隔离实跑、真实使用记录；逐项准确标明，不能将推演称为实跑。无法核实但有意义的风险可单独列为待验证假设及验证方法，不标为已确认或虚构复现。根据具体影响和条件确定优先级，不按缺少某种模式或规则比例自动升级。

## 4. 综合与报告

按重要性而非维度堆叠组织：目标和覆盖范围、最关键的问题与证据、具体触发场景和影响、共同根因、针对性的修改建议、取舍及验收方法。可报告现有有效设计；对未覆盖范围、证据不足和运行环境限制如实说明。默认至多 8 个高价值发现；用户需要更全面时按请求调整，不为凑数输出。参考 [report-templates.md](report-templates.md)。

只请求分析时完成报告即结束；若用户已明确授权修复，将范围内问题标为 accepted，修复前为每项确定验收条件，再进入模式 B，无需逐项重复确认；需要业务取舍、授权不明或高风险操作时再询问。只有用户请求评分时进入模式 D。已有 issue 状态和验收条件可用于同一项目后续修复，台账写入须遵守用户授权和目标项目规则，不默认修改 skill 自身或被审项目文件。
