# Agent PM 审查清单

> 此清单是 agent-pm 技术审查的核心工具。
>
> 维度默认分类为必检/选检，但**具体哪些维度必检取决于项目类型**——参见 SKILL.md 的"各类型审查重点"映射表。不适用的维度直接跳过。
>
> 维度划分原则：每个维度只关注一个层面，不交叉。
> - 指令层：**说什么**
> - 工具层：**用什么做**
> - 工作流层：**怎么做**（路径 + 异常 + 边界）
> - 逻辑正确性：**对不对**（判断、数据、时序、假设）
> - 设计质量：**好不好**（冗余、复杂度、一致性）
> - 最佳实践：**成熟度**（从优秀项目提炼的设计模式，选检）
>
> **标准修复方法**：详见 [extended/checklist-fix-methods.md](extended/checklist-fix-methods.md)

---

## 一、指令层（必检）

审查 system prompt、CLAUDE.md、skill.md 等指令文件的清晰度和完整性。

- [ ] **角色定义明确**——agent 知道自己是谁、该干什么、不该干什么
- [ ] **边界清晰**——明确列出了"不做"的事项，防止越界
- [ ] **约束具体**——不是"输出格式要好"，而是"输出 JSON，包含以下字段..."
- [ ] **触发条件明确**——什么时候启动、什么时候不启动，有明确判断标准
- [ ] **无歧义表述**——每个指令只有一种理解方式，不存在"看情况"
- [ ] **优先级明确**——当多个指令冲突时，有明确的优先级规则
- [ ] **上下文充分**——agent 有足够的背景信息来做判断，而非靠猜

---

## 二、工具层（默认必检，MCP server 必检，skill/CLAUDE.md 选检）

审查 tool description、参数定义、工具之间的关系。若项目本身不定义 tool（如纯指令文件），检查是否引用了外部 tool 以及引用是否准确。

- [ ] **description 精准**——每个 tool 的描述精确说明了"做什么"和"什么时候用"
- [ ] **参数描述无歧义**——每个参数的类型、格式、约束都有明确说明
- [ ] **工具无重叠**——不存在两个 tool 做同一件事的情况
- [ ] **工具无遗漏**——agent 需要的能力都有对应的 tool 覆盖
- [ ] **返回值明确**——tool 的输出格式和字段有定义
- [ ] **错误行为定义**——tool 调用失败时 agent 应该怎么处理
- [ ] **工具依赖关系清晰**——哪些 tool 可以独立使用，哪些需要先调用其他 tool

---

## 三、工作流层（必检）

审查 agent 的执行路径、分支逻辑、异常处理和边界覆盖。关注"流程是否完整"，不关注"逻辑是否正确"（那是维度四的事）。

- [ ] **主路径完整**——从输入到输出的主要流程无断点
- [ ] **分支覆盖**——每个判断节点的所有分支都有处理
- [ ] **异常路径处理**——工具调用失败、输入格式错误、超时等情况有回退方案
- [ ] **循环终止条件**——有循环/重试逻辑的地方有明确的退出条件
- [ ] **状态管理清晰**——agent 在多步执行中如何保持上下文、如何传递状态
- [ ] **无死路**——不存在"走到某一步就卡住无法继续"的情况
- [ ] **输入→处理→输出闭环**——每个输入都有对应的处理和输出路径
- [ ] **反馈闭环**——agent 的输出是否能被用户验证和纠正
- [ ] **边界 case 覆盖**——空输入、极端值、特殊字符等是否有处理路径
- [ ] **审查范围固定**——同一轮审查-修复-验证是否固定 ReviewSpec，避免每轮换标准
- [ ] **发现/验证分离**——修复后的验证是否只验证已确认问题和直接回归，而非重新开放式审查
- [ ] **停止条件明确**——是否定义了何时结束本轮，避免无限修复循环

---

## 四、逻辑正确性（必检）

审查 agent 设计中的逻辑是否正确。关注"判断对不对"，不关注"路径全不全"（那是维度三的事）。

- [ ] **条件判断正确**——if/else 逻辑是否准确反映了业务规则
- [ ] **数据流正确**——数据从 A 到 B 的传递过程中无丢失、无篡改
- [ ] **时序正确**——有先后依赖的操作是否按正确顺序执行
- [ ] **假设合理**——agent 的设计假设是否成立，是否有未验证的假设
- [ ] **因果关系正确**——"做了 A 所以 B 发生"是否真的成立
- [ ] **前置条件验证**——执行操作前是否验证了必要的前置条件
- [ ] **后置条件确认**——操作完成后是否确认了预期结果

---

## 五、设计质量（必检）

审查 agent 项目的设计质量：是否简洁、是否冗余、是否一致。

- [ ] **无重复指令**——同一约束/规则不在多处重复定义
- [ ] **无重复工具**——不存在功能重叠的 tool
- [ ] **无冗余步骤**——执行流程中每一步都有必要，可以删除任何一步都会影响结果
- [ ] **无过度设计**——当前复杂度是否与问题复杂度匹配
- [ ] **无历史遗留**——没有"以前有用但现在不用"的指令或工具
- [ ] **指令-工具-输出一致**——三者之间无矛盾（如指令说"输出 JSON"但 tool 没定义格式）
- [ ] **体积合理**——SKILL.md 行数在合理范围（≤200 行=轻量，200-500 行=适中，>500 行应考虑拆分或精简）；引用文件数量合理（≤3 个为佳）；单个 checklist/模板不宜超过 100 行
- [ ] **问题生命周期可追踪**——是否有稳定 issue_id、状态、验收条件和历史台账
- [ ] **进化机制隔离**——新规则是否先进入候选区，避免立刻污染当前审查标准

---

## 六、输出层（选检）

审查 agent 的输出格式和质量。

- [ ] **格式一致**——输出格式固定，不会随机变化
- [ ] **对下游友好**——输出内容可以直接被下游系统/用户使用
- [ ] **无多余信息**——不包含与任务无关的内容
- [ ] **信息完整**——输出包含了完成任务所需的所有信息
- [ ] **可机读**——如果输出需要被程序解析，格式是否规范

---

## 七、用户交互层（选检）

审查 agent 与用户的交互体验。

- [ ] **触发条件清晰**——用户知道怎么启动这个 agent
- [ ] **边界 case 引导**——当用户输入不当时，agent 给出有用的引导而非报错
- [ ] **skill 间关系明确**——与其他 skill 的调用关系、优先级有定义
- [ ] **用户预期管理**——agent 的能力边界对用户透明
- [ ] **进度反馈**——长时间执行时有中间状态反馈

---

## 八、最佳实践（选检）

审查项目是否具备从优秀 agent 项目中提炼的成熟设计模式。详见 [best-practices.md](best-practices.md)。

缺少最佳实践不一定是 bug（P2/P3），除非缺少某项直接导致了功能逻辑问题（那才是 P0/P1）。

- [ ] **BP-001 Iron Law**——核心流程是否有不可违反的底线规则？
- [ ] **BP-002 Red Flags + Rationalization Table**——是否预判了 agent 的自我欺骗模式？
- [ ] **BP-003 Process Flow Diagram**——多步工作流是否有可视化流程图？
- [ ] **BP-004 Prompt 模板分离**——重复使用的模板是否提取为独立文件？
- [ ] **BP-005 Rigid/Flexible 类型标注**——关键流程是否标注了纪律等级？
- [ ] **BP-006 Description Field 纪律**——skill description 是否只含触发条件？
- [ ] **BP-007 连续执行 + 智能暂停**——多步执行是否默认连续、只在安全点暂停？
- [ ] **BP-008 Token 效率**——主文件是否控制在合理大小？详细流程是否按需加载？
- [ ] **BP-009 设计先行门控**——实现前是否有设计探索和用户批准的 HARD-GATE？
- [ ] **BP-010 两阶段 Review**——代码审查是否先审规格合规、再审代码质量？
- [ ] **BP-011 小任务 + 新鲜上下文**——大任务是否拆分为小任务，每个用独立上下文执行？
- [ ] **BP-012 阶段间结构化交接**——工作流各阶段是否有明确的交接条件和触发动作？
- [ ] **BP-013 Rubric 驱动评估**——是否有结构化评测条目，分级且含负向标准（Pitfall）？
- [ ] **BP-014 迭代循环与退出条件**——执行流程是否有"评估→反馈→改进"闭环和退出条件？
- [ ] **BP-015 品质锚定**——需求阶段是否定义了品质层级、参考锚点和设计意图？
- [ ] **BP-016 目标治理优先**——目标、反馈与必要约束是否适合当前任务？

---

## 九、目标与反馈（按任务需要检查）

检查项目是否定义了与用户任务相符的结果，是否有足够的反馈、验收、必要纠错和可观测性。迭代、量化评分、独立评估和信息隔离都是可选方案：先说明实际失败、影响和为什么当前任务需要它们，再考虑引入；轻量或一次性任务可能无需这些机制。规则数量或比例仅可作为探索线索，不作为质量阈值或严重程度依据。相关改进的依赖和优先级须基于具体因果链判断，不自动连锁升级。

- G-001 评估反馈：结果能否根据合适标准判断？
- G-002 目标定义：是否清楚什么结果对用户有价值？
- G-003 迭代：任务需要时能否依据反馈修正并停止？
- G-004 独立性：重要判断是否需要独立复核，现有证据有何局限？
- G-005 过程与目标：约束是否帮助完成任务，是否造成实际摩擦？
- G-006 可观测性：必要时能否获取可验证的结果？

## 0. 候选问题验证

已确认问题须核对以下相关事项；证据不足但有价值的风险可作为待验证假设单列。

- [ ] **读完上下文**——找到问题涉及的所有相关段落，通读完整上下文。其他段落是否有补充说明、例外条款或分级规则使逻辑自洽？
- [ ] **模拟执行**——用一个具体输入走完整执行路径，推演可能行为是否与问题描述一致；实跑时单独记录实际观察。hook/兜底/降级路径是否会让描述的行为不实际发生？
- [ ] **区分层次**——问题是功能逻辑 bug，还是工具覆盖度/文档表述精度/设计决策偏好？
- [ ] **区分概念与实现**——如果涉及"概念定义"与"实际实现"的差异，实现是否为概念的合理近似？是否有明确优先级规则（如"脚本先判，LLM 兜底"）？
- [ ] **走完逻辑链**——涉及条件判断、计数、状态转换的问题，模拟完整状态流转，不能只看中间一步。

### 反模式清单

命中任一即高度怀疑该问题是误报：

| 反模式 | 正确做法 |
|--------|---------|
| 两处文档措辞不同就报矛盾 | 先找补充说明、例外条款或分级规则 |
| 概念定义和脚本行为有差异就报 bug | 先确认"脚本是实现、概念是框架"的架构 |
| 工具覆盖度问题报成功能逻辑 bug | 降级为工具层问题或淘汰 |
| 只看引文段落没读完整上下文 | 必须通读相关文件完整章节 |
| 没用具体输入模拟执行就报 P0/P1 | 不得报告为 P0/P1 |

## 自定义规则

> 以下规则由 agent-pm 在审查过程中自动提炼，来源于跨项目重复出现的问题。
>
> 格式：`### RXXX: 规则标题`，包含字段：来源（项目名 + 日期）、规则描述、检查方式。

### R001: 主文档与 reference 文件的映射表重复
- **来源**: flutter-forge (2026-05-16)
- **规则**: 当主文档 (SKILL.md) 和 reference 文件 (如 load_map.md) 都维护同一份"场景→文件"映射时，主文档只保留一句指向 reference 的链接，不要内联完整表格。否则两处维护必然产生不一致。
- **检查方式**: 在"按需加载"、"参考文件"等章节中，检查是否存在与 reference 文件重复的表格。

### R002: 多类型项目缺少维度映射
- **来源**: agent-pm (2026-05-16)
- **规则**: 当一个工具支持审查/处理多种类型的项目时，必须明确每种类型对应检查哪些维度。否则 agent 会对不适用的维度强行凑问题（如对纯指令文件检查 tool 设计）。
- **检查方式**: 检查项目是否声明支持多种类型，若有，是否提供了类型→维度的映射表。

### R003: 概念定义与实现脚本的差异不是 bug
- **来源**: flutter-forge (2026-05-19)
- **规则**: 当项目中有"概念定义"（如 SKILL.md 的 10 秒测试）和"实际实现"（如 classify_task.sh 的关键词匹配）时，实现是概念的合理近似。只要存在明确的优先级规则（如"脚本先判，confidence:high 时 LLM 信任脚本"），概念与实现的差异不构成 bug。
- **检查方式**: 发现概念与实现差异时，先确认是否有优先级规则，再确认差异是否导致实际错误行为。

### R004: 文档分级规则下的一致性不等于矛盾
- **来源**: flutter-forge (2026-05-19)
- **规则**: 当两处文档对同一事项有不同表述时，先检查是否存在分级规则（如"轻量任务不写 session，中等及以上写 session"）。分级规则下的差异是一致性设计，不是矛盾。
- **检查方式**: 发现两处表述差异时，先搜索分级/例外/补充说明，确认是否为分级规则下的正常差异。

### R005: 工具覆盖度缺口 ≠ 功能逻辑 bug
- **来源**: flutter-forge (2026-05-19)
- **规则**: 当校验脚本/安全网未覆盖某条 P0 规则时，这是工具层缺口，不是功能逻辑 bug。功能逻辑由 LLM 遵守规则执行，校验脚本是辅助安全网。安全网有洞不等于主逻辑有 bug。
- **检查方式**: 报告前确认：问题是"规则本身不对"还是"规则没有被工具校验"。后者属于工具层。

### R006: 状态流转问题必须模拟完整链路
- **来源**: flutter-forge (2026-05-19)
- **规则**: 涉及计数、状态转换、条件触发的问题，必须模拟从触发条件到最终结果的完整链路。只看中间一步（如"轻量跳过检查"）而忽略前后条件（如"轻量不计入 count"）会导致误报。
- **检查方式**: 对状态流转问题，写出完整的 if/then/else 链路，确认每一步的输入输出。
