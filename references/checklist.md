# Agent PM 审查清单

> 此清单是 agent-pm 技术审查和修复的核心工具。
>
> 维度默认分类为必检/选检，但**具体哪些维度必检取决于项目类型**——参见 SKILL.md 的"各类型审查重点"映射表。不适用的维度直接跳过。
>
> 维度划分原则：每个维度只关注一个层面，不交叉。
> - 指令层：**说什么**
> - 工具层：**用什么做**
> - 工作流层：**怎么做**（路径 + 异常 + 边界）
> - 逻辑正确性：**对不对**（判断、数据、时序、假设）
> - 设计质量：**好不好**（冗余、复杂度、一致性）

---

## 一、指令层（必检）

审查 system prompt、CLAUDE.md、skill.md 等指令文件的清晰度和完整性。

- [ ] **角色定义明确**——agent 知道自己是谁、该干什么、不该干什么
- [ ] **边界清晰**——明确列出了"不做"的事项，防止越界
- [ ] **约束具体**——不是"输出格式要好"，而是"输出 JSON，包含以下字段..."
- [ ] **触发条件明确**——什么时候启动、什么时候不启动，有明确判断标准
- [ ] **无歧义表述**——每个指令只有一种理解方式，不存在"看情况"
- [ ] **优先级明确**——当多个指令冲突时，有明确的优先级规则
- [ ] **上下文充分**——agent 有足够的背景信息来做判断，而非靠猜

### 标准修复方法（指令层）

| 问题类型 | 修复方法 | 适用场景 |
|----------|----------|----------|
| 角色定义模糊 | 重写为"你是 X，你的职责是 Y，你不做 Z"三段式 | 角色描述过于宽泛 |
| 边界不清晰 | 在"不做的事"部分逐条列出排除项 | 缺少明确的排除清单 |
| 约束不具体 | 将模糊描述替换为具体字段/格式/值的定义 | "输出格式要好"类表述 |
| 触发条件模糊 | 添加 if/when 判断条件，明确触发和不触发的边界 | 触发词不明确 |
| 歧义表述 | 重写为无歧义的单一理解方式，消除"看情况" | 存在多种理解方式 |
| 优先级冲突 | 在冲突指令处添加优先级标注（如"当 A 和 B 冲突时，优先 A"） | 多条指令可能矛盾 |
| 上下文不足 | 在相关指令前补充背景信息或引用上下文来源 | agent 需要猜测才能执行 |

---

## 二、工具层（默认必检，MCP server 必检，skill/CLAUDE.md 选检）

审查 tool description、参数定义、工具之间的关系。若项目本身不定义 tool（如纯指令文件），检查是否引用了外部 tool 以及引用是否准确。

- [ ] **description 精准**——每个 tool 的描述精确说明了"做什么"和"什么时候用"
- [ ] **参数描述无歧义**——每个参数的类型、格式、约束都有明确说明
- [ ] **工具无重叠**——不存在两个 tool 做同一件事的情况
- [ ] **工具无遗漏**——agent 需要的能力都有对应的 tool 覆盖
- [ ] **返回值明确**——tool 的输出格式和字段有定义
- [ ] **错误行为定义**——tool 调用失败时 agent 应该怎么处理
- [ ] **工具依赖关系清晰**——哪些 tool 可以独立使用，哪些需要先调用其他 tool

### 标准修复方法（工具层）

| 问题类型 | 修复方法 | 适用场景 |
|----------|----------|----------|
| description 模糊 | 重写为"当用户需要 X 时调用此工具，返回 Y"格式 | 描述不说明用途 |
| 参数缺类型 | 为每个参数添加 type、required、description 字段 | 参数定义不完整 |
| 工具重叠 | 合并功能相近的工具，或明确划分各自职责边界 | 两个 tool 做类似的事 |
| 工具遗漏 | 补充缺失的工具，或在指令中说明如何用现有工具组合实现 | agent 缺少必要能力 |
| 返回值未定义 | 添加 output schema 或返回值示例 | tool 输出格式不明确 |
| 错误行为缺失 | 在 tool description 或 agent 指令中添加错误处理指引 | 调用失败无回退 |
| 依赖关系不清 | 添加"前置条件"字段或在指令中说明调用顺序 | 需要按特定顺序调用 |

---

## 三、工作流层（必检）

审查 agent 的执行路径、分支逻辑、异常处理和边界覆盖。关注"流程是否完整"，不关注"逻辑是否正确"（那是维度四的事）。

- [ ] **主路径完整**——从输入到输出的主要流程无断点
- [ ] **分支覆盖**——每个判断节点的所有分支都有处理
- [ ] **异常路径处理**——工具调用失败、输入格式错误、超时等情况有回退方案
- [ ] **循环终止条件**——有循环/重试逻辑的地方有明确的退出条件
- [ ] **状态管理清晰**——agent 在多步执行中如何保持上下文、如何传递状态
- [ ] **无死路**——不存在"走到某一步就卡住无法继续"的情况
- [ ] **输入→处理→输出闭环**——每个输入都有对应的处理和输出路径
- [ ] **反馈闭环**——agent 的输出是否能被用户验证和纠正
- [ ] **边界 case 覆盖**——空输入、极端值、特殊字符等是否有处理路径

### 标准修复方法（工作流层）

| 问题类型 | 修复方法 | 适用场景 |
|----------|----------|----------|
| 主路径断裂 | 补充缺失的步骤，确保从输入到输出有完整链路 | 流程中间有断点 |
| 分支缺失 | 为每个判断节点补充 else/default 分支 | 只处理了部分分支 |
| 异常无回退 | 添加 try-catch 或 fallback 路径 | 失败后无后续处理 |
| 循环无终止 | 添加最大重试次数或超时条件 | 重试逻辑可能无限循环 |
| 状态丢失 | 在流程步骤间显式传递上下文/状态 | 多步执行丢失信息 |
| 死路 | 删除不可达路径或补充后续处理 | 某步之后无法继续 |
| 边界未覆盖 | 添加空值检查、类型校验、范围限制 | 输入未验证 |

---

## 四、逻辑正确性（必检）

审查 agent 设计中的逻辑是否正确。关注"判断对不对"，不关注"路径全不全"（那是维度三的事）。

- [ ] **条件判断正确**——if/else 逻辑是否准确反映了业务规则
- [ ] **数据流正确**——数据从 A 到 B 的传递过程中无丢失、无篡改
- [ ] **时序正确**——有先后依赖的操作是否按正确顺序执行
- [ ] **假设合理**——agent 的设计假设是否成立，是否有未验证的假设
- [ ] **因果关系正确**——"做了 A 所以 B 发生"是否真的成立
- [ ] **前置条件验证**——执行操作前是否验证了必要的前置条件
- [ ] **后置条件确认**——操作完成后是否确认了预期结果

### 标准修复方法（逻辑正确性）

| 问题类型 | 修复方法 | 适用场景 |
|----------|----------|----------|
| 条件判断错误 | 重写条件表达式，确保准确反映业务规则 | if/else 逻辑与实际不符 |
| 数据流丢失 | 在数据传递链路中添加校验点，确保数据完整性 | 数据在步骤间丢失 |
| 时序错误 | 调整操作顺序，添加依赖检查 | 先执行了后置操作 |
| 假设不合理 | 删除或验证未验证的假设，添加防御性检查 | 基于未验证前提设计 |
| 因果关系错误 | 重新梳理因果链，确保 A 真的导致 B | 推理链有断裂 |
| 前置条件缺失 | 在操作前添加必要的校验步骤 | 直接操作未检查前提 |
| 后置条件缺失 | 在操作后添加结果确认步骤 | 操作后未验证结果 |

---

## 五、设计质量（必检）

审查 agent 项目的设计质量：是否简洁、是否冗余、是否一致。

- [ ] **无重复指令**——同一约束/规则不在多处重复定义
- [ ] **无重复工具**——不存在功能重叠的 tool
- [ ] **无冗余步骤**——执行流程中每一步都有必要，可以删除任何一步都会影响结果
- [ ] **无过度设计**——当前复杂度是否与问题复杂度匹配
- [ ] **无历史遗留**——没有"以前有用但现在不用"的指令或工具
- [ ] **指令-工具-输出一致**——三者之间无矛盾（如指令说"输出 JSON"但 tool 没定义格式）
- [ ] **体积合理**——SKILL.md 行数在合理范围（≤200 行=轻量，200-500 行=适中，>500 行应考虑拆分或精简）；引用文件数量合理（≤3 个为佳）；单个 checklist/模板不宜超过 100 行

### 标准修复方法（设计质量）

| 问题类型 | 修复方法 | 适用场景 |
|----------|----------|----------|
| 指令重复 | 合并为一处定义，其他位置引用 | 同一规则出现在多处 |
| 工具重叠 | 合并或划分职责 | 两个 tool 功能相似 |
| 冗余步骤 | 删除不必要的步骤，简化流程 | 流程中有可以跳过的步骤 |
| 过度设计 | 简化方案，用更少的工具/步骤实现 | 3 个 tool 能搞定用了 10 个 |
| 历史遗留 | 删除不再使用的指令或工具 | 有"以前有用但现在不用"的内容 |
| 三者不一致 | 统一指令、工具、输出的描述 | 指令说的和 tool 做的不匹配 |
| 体积过大 | 拆分为多个 skill/reference 文件、精简冗余描述、合并重复内容 | SKILL.md >500 行或引用文件过多 |

## 六、输出层（选检）

审查 agent 的输出格式和质量。

- [ ] **格式一致**——输出格式固定，不会随机变化
- [ ] **对下游友好**——输出内容可以直接被下游系统/用户使用
- [ ] **无多余信息**——不包含与任务无关的内容
- [ ] **信息完整**——输出包含了完成任务所需的所有信息
- [ ] **可机读**——如果输出需要被程序解析，格式是否规范

### 标准修复方法（输出层）

| 问题类型 | 修复方法 | 适用场景 |
|----------|----------|----------|
| 格式不一致 | 定义固定输出模板，强制使用 | 输出格式每次不同 |
| 对下游不友好 | 重新设计输出结构，适配下游消费方式 | 输出需要二次加工 |
| 多余信息 | 删除与任务无关的输出内容 | 输出包含噪音 |
| 信息不完整 | 补充缺失的输出字段 | 输出缺少关键信息 |
| 不可机读 | 规范化输出格式（JSON/YAML/TOML） | 输出需要被程序解析 |

---

## 七、用户交互层（选检）

审查 agent 与用户的交互体验。

- [ ] **触发条件清晰**——用户知道怎么启动这个 agent
- [ ] **边界 case 引导**——当用户输入不当时，agent 给出有用的引导而非报错
- [ ] **skill 间关系明确**——与其他 skill 的调用关系、优先级有定义
- [ ] **用户预期管理**——agent 的能力边界对用户透明
- [ ] **进度反馈**——长时间执行时有中间状态反馈

### 标准修复方法（用户交互层）

| 问题类型 | 修复方法 | 适用场景 |
|----------|----------|----------|
| 触发不清晰 | 明确写出手动触发方式和自动触发条件 | 用户不知道怎么用 |
| 边界引导缺失 | 添加输入校验和友好错误提示 | 用户输入不当时无反馈 |
| skill 关系不清 | 在指令中声明与其他 skill 的调用/依赖关系 | 多 skill 协作不明确 |
| 预期不透明 | 在指令中明确能力边界和限制 | 用户对能力有误解 |
| 缺少进度反馈 | 在长流程中添加阶段性输出 | 长时间执行无反馈 |

## 自定义规则

> 以下规则由 agent-pm 在审查过程中自动提炼，来源于跨项目重复出现的问题。
>
> 格式：`### RXXX: 规则标题`，包含字段：来源（项目名 + 日期）、规则描述、检查方式。

### R001: 主文档与 reference 文件的映射表重复
- **来源**: flutter-forge (2026-05-16)
- **规则**: 当主文档 (SKILL.md) 和 reference 文件 (如 load_map.md) 都维护同一份"场景→文件"映射时，主文档只保留一句指向 reference 的链接，不要内联完整表格。否则两处维护必然产生不一致。
- **检查方式**: 在"按需加载"、"参考文件"等章节中，检查是否存在与 reference 文件重复的表格。

### R002: 多类型项目缺少维度映射
- **来源**: agent-pm (2026-05-16)
- **规则**: 当一个工具支持审查/处理多种类型的项目时，必须明确每种类型对应检查哪些维度。否则 agent 会对不适用的维度强行凑问题（如对纯指令文件检查 tool 设计）。
- **检查方式**: 检查项目是否声明支持多种类型，若有，是否提供了类型→维度的映射表。
