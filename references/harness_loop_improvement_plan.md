## Agent-PM 改进方案：融合 Harness Engineering + Loop Engineering 视角

目标：让 agent-pm 在审查项目时自动检查"目标治理"能力，在创建新 skill 时引导用户设计评估反馈和迭代循环。

---

### 核心判断

agent-pm 当前的 8 大审查维度覆盖了"说什么"（指令层）、"用什么做"（工具层）、"怎么做"（工作流层）、"对不对"（逻辑正确性）、"好不好"（设计质量）、输出、交互和最佳实践。这些维度对 **指令清晰度和逻辑完整性** 的审查已经非常成熟。

但它缺少一个关键视角：**这个项目能不能驱动 Agent 产出高质量结果？**

具体来说，agent-pm 目前不会检查：
- 项目是否有量化评估体系来回答"做得有多好"？
- 项目是否有迭代循环让 Agent 基于评估结果持续改进？
- 项目的"目标定义"是否足够丰富，能让 Agent 知道"做成什么样算好"？
- 项目的过程控制和目标治理是否平衡？

这些恰好是两篇文章的核心洞察。

### 改进一：新增审查维度 — 目标治理层

**影响范围**：`checklist.md` 新增维度九，`SKILL.md` 审查范围表增加该维度

#### 新增维度九：目标治理层（必检）

关注"能不能驱动好结果"。这个维度不检查指令写得清不清楚（那是维度一），而是检查项目是否为 Agent 配备了足够的目标定义、评估反馈和迭代改进能力。

**检查项**：

| 编号 | 检查项 | 问题描述 | 严重程度参考 |
|------|--------|---------|-------------|
| G-001 | 评估反馈体系 | 项目是否有结构化的评估机制来回答"做得有多好"（而不仅是"做对了吗"）？ | 缺失=P2，二元判定=P3 |
| G-002 | 目标定义丰富度 | 项目是否定义了"做成什么样算好"（品质标准、参考锚点），而不仅是"做什么算对"（功能验收）？ | 缺失=P2 |
| G-003 | 迭代循环设计 | 项目的执行流程是否有"评估→反馈→改进"的循环？循环是否有退出条件（评分阈值、最大轮次、边际效益判断）？ | 无循环=P1，无退出条件=P2 |
| G-004 | 执行者与评估者分离 | 执行角色和评估角色是否信息隔离？评估者是否能看到执行者的思路（导致正面偏见）？执行者是否能看到评估标准（导致针对性优化）？ | 未分离=P2，共享上下文=P2 |
| G-005 | 过程控制与目标治理平衡 | 项目的规则/门禁/约束中，有多少在帮 Agent 理解目标（目标治理），有多少在限制 Agent 行为（过程控制）？如果后者远多于前者，系统可能过于僵硬。 | 严重失衡=P3 |
| G-006 | 可观测性 | Agent 在执行过程中能否"观察"到结果（截图、DOM 快照、日志、测试输出）？如果 Agent 写完代码后是"盲的"，循环就断在 observe 环节。 | 完全无可观测性=P2 |

**审查方法**：
1. 检查项目的 SKILL.md / 主指令文件中是否有评估/评分/Rubric 相关机制
2. 检查是否有迭代循环（while 循环、重试、多轮评估）以及退出条件
3. 检查需求/目标定义中是否包含品质维度（品质层级、参考锚点、设计意图）
4. 检查执行角色和评估角色是否分离，上下文是否隔离
5. 统计"过程控制规则"和"目标治理规则"的比例
6. 检查 Agent 是否有获取运行结果的能力（截图、测试输出等）

**标准修复方法**：

| 问题 | 修复方向 |
|------|---------|
| 无评估体系 | 建议引入 Rubric 评测框架：四层（功能/健壮/UI/交互）× 四级权重（Essential/Important/Optional/Pitfall） |
| 目标定义单薄 | 建议在需求阶段增加品质锚定：品质层级 + 正面/反面参考 + 设计意图关键词 |
| 无迭代循环 | 建议增加"评估→改进→再评估"循环，设评分阈值和最大轮次作为退出条件 |
| 角色未隔离 | 建议分离执行者和评估者上下文，评估者不看执行思路，执行者不看评测标准 |
| 过程控制过重 | 建议审查现有规则：每条规则问"是在帮 Agent 理解目标，还是在限制行为？"，考虑精简后者 |
| 无可观测性 | 建议增加 Agent 获取运行结果的能力（截图脚本、测试输出解析等） |

**注意**：此维度对不同类型的 agent 项目权重不同：
- **开发类 skill**（如 flutter-forge、h5-forge）：全部 6 项必检
- **工具类 skill**（如代码格式化、文件处理）：G-001/G-003/G-006 必检，其余选检
- **纯指令类**（如 CLAUDE.md）：G-001/G-005 必检，其余选检
- **MCP Server**：G-006 必检，其余选检

### 改进二：模式 C 增加目标治理追问维度

**影响范围**：`mode-c.md` 增加闭环条件，`skill-brief-questions.md` 增加提问维度

#### 新增闭环条件（第 9 条）

在现有 8 个闭环条件（价值/触发/边界/输入/流程/输出/资源/验收）基础上增加：

**9. 评估与迭代闭环**：清楚如何评估 Agent 的产出质量（不仅是"对不对"还有"好不好"），有迭代改进循环和退出条件。

闭环标准：
- 有量化评估方案（Rubric 条目、评分维度或检查清单）
- 有迭代循环设计（评估不达标时如何回到执行阶段重做）
- 有退出条件（评分阈值 / 最大轮次 / 边际效益判断）
- 有执行者/评估者的信息隔离策略

#### skill-brief-questions.md 新增提问维度

**10. 评估与迭代**

- 你希望怎么判断 Agent 的产出是"好的"？只是功能对，还是品质也要达标？
- 如果 Agent 第一次做得不好，流程中有没有让它看到评估结果并改进的环节？
- 改进循环最多跑几轮？什么时候该接受当前结果不再迭代？
- 执行者和评估者需要信息隔离吗？执行者能看到评测标准吗？
- Agent 在执行过程中能"看到"运行结果吗（截图、测试输出、DOM 快照）？

**闭环标准**：有评估方案、迭代循环、退出条件和信息隔离策略。

#### SkillBrief YAML 新增字段

```yaml
evaluation:
  evaluation_method: "rubric / checklist / binary / none"
  evaluation_dimensions: []        # 评估维度
  iteration_loop:
    enabled: true
    exit_conditions: "score_threshold / max_rounds / marginal_stall"
    max_rounds: 5
    score_threshold: 4.0
  information_isolation:
    executor_sees_rubric: false
    evaluator_sees_implementation_notes: false
  observability:
    method: "screenshot / test_output / dom_snapshot / none"
```

### 改进三：新增最佳实践

**影响范围**：`best-practices.md` 新增 BP-013 到 BP-016

#### BP-013: Rubric 驱动评估（Rubric-Driven Evaluation）

项目为 Agent 配备结构化的评测框架，把"什么是好"拆成可独立判断、可量化加权的检查条目，而非仅靠二元 pass/fail 或 Agent 自我评估。

核心要素：
- 评测条目分级（Essential / Important / Optional / Pitfall）
- 负向标准（Pitfall）与正向标准并列
- 每条条目自包含可评判，不依赖外部上下文
- 评测条目在需求阶段就生成，不在评估阶段临时发挥

审查检查点：
- 项目是否有评测条目？条目是否分级？
- 是否有 Pitfall（负向标准）？
- 条目是否在需求阶段生成？

修复建议：引入四层 Rubric 框架（功能正确性 / 健壮性 / UI 呈现 / 交互体验），在需求确认阶段生成评测条目。

#### BP-014: 迭代循环与退出条件（Iteration Loop with Exit Conditions）

项目的执行流程包含"评估→反馈→改进"的闭环，且有明确的退出条件防止无限循环或过早结束。

核心要素：
- 评分不达标时回到执行阶段重做
- 最大轮次限制（防止无限循环）
- 评分阈值（达标即退出）
- 边际效益判断（连续多轮提升微弱时建议退出）

审查检查点：
- 执行流程是线性的还是有循环？
- 循环有无退出条件？
- 有无边际效益判断？

修复建议：在验证阶段后增加迭代循环逻辑，设评分阈值和最大轮次。

#### BP-015: 品质锚定（Quality Anchoring）

项目在需求阶段就定义"做成什么样算好"，给 Agent 具象化的品质标杆，而非仅定义"做什么算对"。

核心要素：
- 品质层级（MVP / 精打磨 / 生产级）
- 正面参考（截图/URL + "好在哪"）
- 反面参考（"为什么不好"）
- 设计意图关键词（风格、密度、交互范式）
- 品质红线（不可低于此标准）

审查检查点：
- 需求定义中是否有品质维度？
- 是否有参考锚点？
- 品质定位是否传导到评估权重？

修复建议：在需求确认阶段增加品质锚定字段（quality_tier、references、design_intent）。

#### BP-016: 目标治理优先（Goal Governance over Process Control）

项目的规则/约束中，帮助 Agent 理解目标（"做什么""什么是好"）的规则应多于限制 Agent 行为（"不许做什么""必须按这个步骤"）的规则。当过程控制远多于目标治理时，系统趋于僵硬。

核心要素：
- 每条规则可以问："是在帮 Agent 理解目标，还是在限制行为？"
- 目标治理类规则占比不低于 30%
- 不在过程控制上无限叠加，优先强化目标端

审查检查点：
- 统计项目中所有"必须/禁止/不得"类规则的数量
- 统计项目中"目标/验收/品质/评估"类规则的数量
- 比例是否严重失衡（如过程控制 > 80%）？

修复建议：审查现有规则，将纯过程控制类规则考虑精简或合并，增加目标治理类规则。

### 改进四：产品评审增加"Loop 成熟度"维度 + 目标治理综合分析

**影响范围**：`report-templates.md` 产品评审部分，`mode-a.md` 阶段二流程

#### 4a. 新增评分维度

在产品评审的"价值评定"中新增第 5 个评分维度：

**Loop 成熟度** (1-5)：项目的"目标定义 + 评估反馈 + 迭代循环"设计是否完备？能否驱动 Agent 在长时自主运行中持续改进？

评分锚点：
- 1 分：无评估体系，无迭代循环，Agent 一次执行就结束
- 2 分：有二元 pass/fail 验证，但无量化评分和迭代
- 3 分：有评估体系和迭代循环，但缺少品质锚定或退出条件
- 4 分：有 Rubric 评测、迭代循环、品质锚定和退出条件
- 5 分：以上全部 + 信息隔离 + 可观测性 + 边际效益判断

#### 4b. 产品评审增加"目标治理综合分析"步骤

这是最关键的新增。逐维度扫描只能发现"缺了什么"，但无法产出"这些东西之间的关系是什么""为什么缺这个比缺那个更致命""怎么补才能产生协同效应"这种综合判断。

在模式 A 阶段二（产品评审）中，价值评定和发展方向之间新增一个步骤：

**目标治理综合分析**（必出）

此步骤不是列问题清单，而是从整体上回答三个核心问题：

1. **过程控制 vs 目标治理的张力在哪？**
   - 统计项目中"必须/禁止/不得"类规则（过程控制）和"目标/验收/品质/评估"类规则（目标治理）的数量和比例
   - 判断：项目的能量主要花在"确保 Agent 不走错路"还是"帮 Agent 理解什么是好结果"？
   - 如果过程控制远多于目标治理（如 > 80%），指出这个失衡并给出具体例子

2. **最有杠杆的改进方向是什么？**
   - 不是列出所有缺失项，而是判断：补哪一项能让其他项自然改善？
   - 典型判断：如果项目缺评估体系，那即使加更多门禁也不会改善产出质量——因为门禁只防止走错路，不驱动走向好结果
   - 给出 1-2 个最高杠杆改进方向，说明为什么

3. **改进项之间的依赖关系是什么？**
   - 画出关键依赖：哪些改进必须同步实施，哪些有先后顺序
   - 典型依赖：评估体系（Rubric）和迭代循环互为依赖——没有评分就没有循环的驱动力

输出格式：

```markdown
### 目标治理综合分析

**过程控制 vs 目标治理**：
- 过程控制规则：X 条（列举主要规则）
- 目标治理规则：Y 条（列举主要规则）
- 比例：X:Y
- 判断：[平衡 / 偏向过程控制 / 偏向目标治理]
- 具体分析：[2-3 句话说明张力在哪]

**最高杠杆改进方向**：
1. [方向名] — [为什么这个最有杠杆，补了它能连带改善什么]
2. [方向名] — [同上]

**改进依赖关系**：
- [A] 和 [B] 必须同步实施，因为 [原因]
- [C] 应在 [A+B] 之后，因为 [原因]
- [D] 可独立实施
```

**落地建议**：修改 `mode-a.md` 阶段二流程，在"价值评定"和"发展方向"之间插入"目标治理综合分析"步骤。修改 `report-templates.md` 产品评审模板，增加该步骤的输出格式。

### 改进五：进化机制增加 Harness 候选规则

**影响范围**：`issue-ledger.md` 候选规则部分

- **CR-005**: 过程控制规则占比超过 80% 的项目，Agent 行为趋于僵硬和合规导向

### 第二轮改进：基于 flutter-forge 审查实战的方法论补强（2026-06-10）

> 来源：用改进后的 agent-pm 审查 flutter-forge，交叉对照 `harness_improvement_analysis.md` 后发现的 5 个方法论缝隙。

#### 改进六：自诊断材料主动检索

**问题**：Step 1 只检查 issue-ledger.md，不扫描 archive 目录下的自诊断文档。结果是 agent-pm 从零开始扫描，最后交叉对照时才发现项目自己早就知道这些问题。

**改动**：`mode-a.md` Step 1 新增一条——检查 `references/archive/` 目录是否存在自诊断文档或历史审查报告，若有则先读取并纳入扫描上下文。审查目标从"从零发现"调整为"验证自诊断是否准确、改进方案是否已落地"。

#### 改进七：严重程度依赖链升级

**问题**：G-002（品质锚定）在 checklist 中写死 P2，但它是 G-001（Rubric）的前置依赖。当 G-001 确认为 P1 时，G-002 应该自动升级为 P1，否则修复计划会遗漏配套改进。

**改动**：`checklist.md` 维度 9 新增"检查项依赖关系与严重程度升级"部分，包含依赖图和升级规则（P3→P2、P2→P1）。

#### 改进八：BP/G 双向索引

**问题**：BP-013~016（最佳实践，选检）和 G-001~006（目标治理层，必检）检查同一件事，但两套编号独立运作，审查者会困惑用哪个。

**改动**：`checklist.md` 维度 9 新增"对应最佳实践"映射表（G→BP）；`best-practices.md` BP-013~016 各新增"对应检查项"行（BP→G）。审查时以 G 为主线，BP 作为补充参考。

#### 改进九：报告增加"实现提示"字段

**问题**：finding 的"建议"字段只要求"修改方向"，对于复杂改进（如引入 Rubric、设计迭代循环）不够操作。改进分析文档给出了完整的 YAML schema、决策树和落地文件清单，但 agent-pm 的报告模板没有这个位置。

**改动**：`report-templates.md` 技术审查模板在"建议"和"验收条件"之间新增"实现提示"可选字段。维度 9 类改进建议必填，简单 bug 修复不填。

#### 改进十：跨维度综合发现步骤

**问题**：技术审查按维度逐个扫描，但维度之间的发现关系（共同根因、修复级联效应）只在产品评审的综合分析中才体现，技术审查本身没有整体校验。
